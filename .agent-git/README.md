# agent-git

Claude Code와 Codex가 팀의 git 규칙(협업일지 1~5장)을 지키게 하는 패키지입니다. 저장소 안에만 설치되고, 전역 설정은 건드리지 않습니다.

에이전트가 하는 일은 네 단계입니다.

1. 첫 파일을 고치기 전에 작업 유형을 정하고, 최신 `dev`에서 `feature/조명-프리셋` 같은 작업 브랜치를 만듭니다. Orca가 만든 워크트리라면 Orca 브랜치의 이름을 바꿔서 씁니다.
2. 커밋은 `feature: 설명` 형식으로 하고, 커밋할 때마다 자동으로 push합니다.
3. 작업이 끝나면 무엇을 했는지 요약하고 "PR을 올릴까요?"라고 묻습니다.
4. 올리기로 하면 작업 유형과 영역에 맞는 템플릿을 채워 한국어 PR을 `dev`로 올립니다.

## 설치 (한 사람이 한 번)

1. 이 `.agent-git` 폴더를 A 저장소의 맨 위 폴더에 복사합니다.
2. Orca 터미널에서 에이전트에게 "`.agent-git/README.md` 보고 설치해줘"라고 말합니다. 직접 하려면 아래 명령을 실행합니다. 맥에서는 `python` 대신 `python3`을 씁니다.

   ```
   python .agent-git/flow.py install
   ```

   설치 스크립트가 하는 일은 다음과 같습니다.
   - 원격에 `dev`가 없으면 `main`에서 만들어 올립니다.
   - `chore/agent-git-setup` 브랜치로 옮깁니다.
   - `.claude/settings.json`, `.codex/hooks.json`, `.codex/config.toml`, `CLAUDE.md`, `AGENTS.md`에 필요한 부분만 덧붙입니다. 기존 내용은 지우지 않습니다.
3. 바뀐 파일을 커밋하고 PR을 올려 `dev`에 머지합니다. 에이전트에게 "커밋하고 PR 올려줘"라고 해도 됩니다.
4. GitHub 기본 브랜치를 `dev`로 바꿉니다. Orca는 새 워크트리를 기본 브랜치에서 만드는데, 규칙이 `main`에 들어가는 것은 첫 통합 PR 이후이기 때문입니다.

   ```
   gh repo edit --default-branch dev
   ```

5. 점검합니다.

   ```
   git agent doctor
   ```

팀원은 `dev`를 pull하기만 하면 됩니다. 훅 파일이 저장소에 들어 있어서 따로 설치할 것이 없습니다.

## 준비물

| 항목 | 이유 | 설치 |
| --- | --- | --- |
| Python 3.8 이상 | 훅 스크립트 실행 | 대부분 이미 있습니다 |
| GitHub CLI (`gh`) | PR 올리기 | Windows `winget install --id GitHub.cli`, 맥 `brew install gh` 뒤 `gh auth login` |

Codex를 쓴다면 처음 한 번 승인이 필요합니다. 이 폴더에서 Codex를 처음 열면 폴더 신뢰와 훅 신뢰를 묻는데, 둘 다 승인해야 합니다. Codex는 승인을 폴더 경로별로 기억하기 때문에, Orca에서 워크트리를 새로 만들면 그 워크트리에서 다시 승인해야 합니다. 승인하지 않으면 규칙 안내만 전달되고 브랜치 차단, 자동 push, PR 질문은 동작하지 않습니다.

## 작업 특징 구조

작업 하나를 두 축으로 나눕니다. 유형은 무엇을 했는지이고, 영역은 어디를 건드렸는지입니다.

### 유형 (하나만 고릅니다)

위에서부터 차례로 묻고 처음 "예"가 나오는 유형을 고릅니다.

| 유형 | 이름 | 판단 질문 | PR에 붙는 칸 |
| --- | --- | --- | --- |
| `fix` | 수정 | 의도와 다르게 동작하던 것을 바로잡았나? | 증상, 원인, 고친 방법, 고른 방법과 이유 |
| `feature` | 기능 | 새로 할 수 있는 일이 생겼나? 새 모델, 프롬프트, 설정을 시도했나? | 왜 필요한가, 무엇이 바뀌었나, 고른 방법과 이유 |
| `refactor` | 구조 개선 | 동작은 같고 구조만 바뀌었나? | 왜 바꾸었나, 무엇이 바뀌었나, 동작이 같다는 근거 |
| `test` | 테스트 | 테스트나 검증 코드만 바뀌었나? | 무엇을 검증하나, 실행 방법, 실행 결과 |
| `docs` | 문서 | 문서와 주석만 바뀌었나? | 누가 읽는 문서인가, 무엇이 바뀌었나 |
| `style` | 서식 | 의미 변화 없이 서식만 바뀌었나? | 적용 범위, 동작 변화 없음 확인 |
| `chore` | 환경 설정 | 의존성, 설정, 도구만 바뀌었나? | 무엇이 바뀌었나, 팀원이 해야 할 일 |

여러 유형이 섞이면 사용자가 요청한 목적을 따릅니다. 테스트와 문서를 함께 고쳤더라도 목적이 기능 추가라면 유형은 `feature`이고, 나머지는 PR의 '함께 바뀐 것' 칸에 적습니다. 목적이 애매하면 표의 위쪽 유형이 이깁니다.

유형은 요청을 보고 먼저 정하고, PR을 올리기 전에 실제로 바뀐 파일로 다시 확인합니다. 둘이 다르면 에이전트가 알려 줍니다. 아직 push하기 전이면 브랜치 이름을 바꾸고, 이미 push했다면 이름은 두고 PR 제목과 템플릿만 실제 유형을 따릅니다.

### 영역 (없거나 여러 개)

| 영역 | 이름 | PR에 붙는 칸 |
| --- | --- | --- |
| `screen` | 화면 | 화면 변경, 전후 이미지 |
| `server` | 서버 | 요청과 응답 예시 |
| `serving` | 서빙 | 실행 방법, 응답 시간, 그래픽 메모리 |
| `image` | 이미지 생성 | 생성 조건 표, 전후 이미지 |
| `copy` | 문구 생성 | 프롬프트 변경, 입력과 출력 예시 |
| `eval` | 평가 | 사진 세트, 지표 표 |

영역은 `config.json`의 경로 규칙으로 먼저 정하고, 규칙에 없는 파일은 에이전트가 판단합니다. 첫 번째 영역이 PR 제목에 들어갑니다.

### PR 모양

제목은 `[기능/이미지 생성] 제품 사진 조명 프리셋 추가` 형식입니다. 본문은 다음 순서로 조립됩니다.

1. 한 줄 요약
2. 유형별 칸
3. 영역별 칸
4. 확인 방법, 함께 바뀐 것, 남은 일, 관련 이슈
5. 자동으로 만드는 바뀐 파일 목록

라벨에는 유형과 영역이 붙습니다. 리뷰어는 영역 담당자, 담당자는 PR을 올린 사람으로 지정됩니다.

`git agent pr`은 올리기 전에 문장을 검사하고, 다음 경우 되돌려 보냅니다.
- 백틱 밖에 영어 단어가 있는 경우
- 한 문장에 백틱이 3개 이상인 경우
- 같은 이름을 두 번 이상 백틱으로 쓴 경우
- 채우지 않은 칸이나 빈 제목이 있는 경우

PR을 올리면 협업일지의 개인 작업 기록 형식으로 초안도 만듭니다. 초안은 커밋되지 않고 `.agent-git/local/journal/`에만 남으므로, 오후 6시 일지를 쓸 때 복사해 붙이면 됩니다.

`dev`를 `main`에 반영할 때는 "통합 PR 올려줘"라고 말합니다. 지난 반영 이후 `dev`에 머지된 PR이 유형별로 자동 정리되고, 통합 테스트 결과는 에이전트가 채웁니다.

## 설정 채우기 (`config.json`)

주제와 폴더 구조가 정해지면 영역별 `paths`와 `reviewers`를 채웁니다. 비워 두어도 동작하고, 그동안은 에이전트가 영역을 판단합니다.

```json
"image": {"label": "이미지 생성", "paths": ["pipeline/relight/*", "models/*"], "reviewers": ["github-id"]}
```

## 훅이 막는 것

| 상황 | 결과 |
| --- | --- |
| `main`, `dev`, Orca 기본 브랜치에서 저장소 파일 수정이나 커밋 | 작업 브랜치부터 만들라고 안내 |
| 커밋 메시지가 `유형: 설명` 형식이 아님 | 형식 안내 |
| `main`이나 `dev`로 push, 강제 push, `git reset --hard` | 차단 |
| `gh pr create` 직접 실행, 에이전트의 PR 머지 | 차단. PR은 `git agent pr`로만, 머지는 리뷰어가 합니다 |

저장소 밖의 파일 수정과 질문만 하는 대화는 막지 않습니다. 훅에 오류가 나도 작업을 멈추지 않고 그냥 통과시킵니다.

## 문제 해결

먼저 `git agent doctor`를 실행해 빨간 항목부터 고칩니다.

| 증상 | 해결 |
| --- | --- |
| `git agent`라는 명령이 없다고 나옴 | 에이전트를 한 번 새로 열면 자동으로 등록됩니다. 또는 `python .agent-git/flow.py doctor` |
| Orca 새 워크트리에서 규칙이 동작하지 않음 | 그 워크트리가 `main`에서 만들어졌는지 확인합니다. 기본 브랜치를 `dev`로 바꾸거나 Orca에서 기준 브랜치를 `dev`로 고릅니다 |
| Codex에서만 동작하지 않음 | 그 워크트리에서 훅 신뢰를 승인했는지 확인합니다 |
| PR 올리기가 `gh` 때문에 멈춤 | 준비물 표대로 설치하고 `gh auth login` |
| 자동 push 실패 | 네트워크나 로그인 문제입니다. 에이전트가 다시 시도할 명령을 알려 줍니다 |

## 파일 구성

| 파일 | 내용 |
| --- | --- |
| `RULES.md` | 에이전트용 영어 지침서. Claude는 `CLAUDE.md`에서, Codex는 세션 시작 훅에서 읽습니다 |
| `flow.py` | 훅과 `git agent` 명령 전부. 표준 라이브러리만 씁니다 |
| `run.sh` | 맥과 윈도우에서 Python을 찾아 `flow.py`를 실행합니다 |
| `config.json` | 유형, 영역, 경로 규칙, 리뷰어 |
| `templates/` | PR 조각. `types/`는 유형별, `areas/`는 영역별입니다 |
| `test_flow.py` | 자체 점검. 패키지를 고친 뒤 `python .agent-git/test_flow.py`로 실행합니다 |
